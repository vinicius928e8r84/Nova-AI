# O `novaproxy` declara à mão a API do SCPreferences, não exige o lock e fala SOCKS4, SOCKS4a, SOCKS5 e HTTP

`SCPreferences` é API de macOS: o SDK do iOS a marca como indisponível, mas o framework exporta os símbolos (é o que o `networksetup` usa no macOS). O `SysProxy.m` a declara na mão para poder usá-la no iPhone com root. No iPhone o serviço Wi-Fi não vem com `Type = IEEE80211`: ele aparece com `Interface.Hardware = "AirPort"`, `Type = "Ethernet"` e nome `Wi-Fi`, e é por isso que `isWifiService` aceita qualquer um dos sinais. No iOS o lock do `SCPreferences` pode não ser suportado; o iOS-ProxyTool ignora o retorno e o commit funciona, e o `novaproxy` segue o mesmo caminho: só soltar o lock se ele foi obtido e, se o commit falhar sem lock, acrescentar isso à mensagem de erro.

O forwarder sobe o proxy HTTP local (`127.0.0.1:localPort`, por padrão 8899) e encaminha tudo pelo upstream, em primeiro plano, porque o `launchd` o mantém vivo. O túnel respeita o esquema: SOCKS5/SOCKS5h, SOCKS4/SOCKS4a e HTTP (`CONNECT`). No SOCKS4a o endereço vai como `0.0.0.1` e o proxy resolve o nome do alvo; o SOCKS4 exige IPv4. Uma resposta que não começa com `0x00` não é SOCKS4: ou o servidor fala SOCKS5 (`0x05`) ou devolveu texto, e nos dois casos esse proxy não serve por SOCKS4. `https` (TLS até o proxy) ainda não é suportado e devolve -1 com erro claro. A leitura da string do proxy está no ADR 0031.

Os testes (`teste/rodar.sh`, `parse_test.m` e `upstream_test.m`) compilam e rodam no Mac, sem tocar no iPhone: o de `upstream_connect` usa proxies falsos locais e confere o que realmente vai no fio (o `CONNECT` com Basic auth, o SOCKS4a, a recusa do proxy e o caso `https`), então nada sai para a internet.
